# board-skills：发版（release.md）

`/board-skills` 的分文件：人新建的卡明确要求发版时读这一份。卡片照常按 work.md「处理一张卡片」领取、交审，开工、推送、打 tag 按下面做。发版由人决定：不主动发版、不顺手打 tag、不改版本号。

只在**人新建的卡明确要求发版**时做：`board start --json` 的动态里第一条是「人」新建了卡片，并且标题或描述要求发布新版本。agent 建的、拆出来的卡，或者只是顺带提到「之后要发版」的卡，都不发：做完卡片本身，交审评论里提一句。

1. **认发版流程**：仓库根目录 AGENTS.md / CLAUDE.md 写了发版命令或流程（例如 Board 的 `<服务器目录>/deploy/release-lan.sh <版本号>`）就照它做，下面几步里它已经覆盖的不重复做。没写时按下面的通用做法。
2. **定版本号**：卡片写了版本号就用它；没写时按仓库写明的规则；仓库也没写时，上一个版本 tag（`git tag --sort=-v:refname`，`v` 加数字开头）的最后一位加 1。这一版的提交里（`git log <上一个 tag>..origin/main`）有 `refactor`、标了「不兼容」的提交，或者你判断算大升级时：停下来按 work.md「处理一张卡片」第 6 步交给人，评论里列出这些提交，问升哪一位。远端已经有同名 tag 时（`git ls-remote --tags origin`）同样交给人，不覆盖。
3. **改版本号、写发版记录**（按 work.md「开工」在最新集成分支上做）：用仓库已有的脚本改版本号（例如 `scripts/bump-version.mjs`），没有脚本就改仓库里所有写版本号的文件；仓库有 `CHANGELOG.md` 这类发版记录时，按它的格式补上这一版。已经是目标版本、也没有发版记录要写时跳过本步，这张卡不提交，直接第 5 步。
4. **推发版提交**：按 work.md「推送」推到集成分支（跑检查、`board land`），提交说明第一行 `chore: 发版 vX.Y.Z`（照仓库的提交规范）。
5. **打 tag**：在集成分支上要发的那个提交（第 4 步推上去的，跳过第 4 步时是最新的 `origin/main`）打注释 tag，正文是上一个 tag 之后的变更说明（按提交整理，写给用户看），多行正文写进文件再传：

   ```sh
   git fetch origin
   git tag -a vX.Y.Z -F <说明文件> <提交>
   ```

   打之前确认这个提交跑过仓库规定的全部检查（第 4 步跑过的就是它；跳过第 4 步时在它上面跑一遍），再 `board hold <ID>`；`NOT_HOLDER` 时不推 tag，删掉本地 tag，按 work.md「推送」第 3 步 `NOT_HOLDER` 那条结束这张卡。
6. **推 tag**：`git push origin vX.Y.Z`。推 tag 通常会触发仓库的 Release 流水线；推出去之后**不改、不删、不挪**，发错了再发一个版本。
7. **同步里程碑**：在仓库目录执行 `board versions sync vX.Y.Z`（不用 `--as`、`--board`），给这一版做的卡片打上版本标签，界面「里程碑」里按版本看。仓库的发版命令已经代跑过的不重复跑；失败（命令不认识、服务端还不认这个接口）时把输出写进交审评论，不重试、不当成发版失败。
8. **交审**：按 work.md「处理一张卡片」第 5 步交审。评论写版本号和为什么是这一位、tag 打在哪个提交、Release 流水线的链接（有的话，例如 `gh run list --workflow <文件> --limit 1`）、`board versions sync` 的输出；最后四行照常写，跳过第 4 步时「提交：」写「无（版本号已是 vX.Y.Z，tag 打在 <sha>）」。

**人工确认项**：仓库 AGENTS.md / CLAUDE.md 发版一节里写明发版前必须做的事（真机验证、确认密钥之类），你做不了的，在第 5 步之前停下来，按 work.md「处理一张卡片」第 6 步交给人，评论里列出来。其他文档里的提醒（待办清单、注意事项）不挡发版，列进交审评论。
