# board-skills：处理卡片（work.md）

`/board-skills` 的分文件：会话开始和结束、处理一张卡片、处理一块白板、代码（worktree、开工、推送、做不下去、发版）。先读 SKILL.md（参数、快捷提示词、规则）；工作流、认角色、常用命令、错误码在 reference.md，拆解建卡和整理未整理在 plan.md，由 board host 启动的会话在 host.md。

## 会话开始

每个会话开始时做一次（处理卡片、白板、一句话需求之前）。由 board host 启动的会话只做第 0、2、3 步（见 host.md）：

0. **`board` 命令**：用 skill 自带的 `<skill 目录>/scripts/board`（Windows：`<skill 目录>\scripts\board.cmd`），本 skill 各文件里写的 `board` 都指它。它运行 skill 目录里本平台的二进制（`bin/<平台>/board`，平台是 darwin-arm64、darwin-x64、linux-x64、linux-arm64、windows-x64），没有时用 PATH 里的 `board`；两个都没有时它会报错，告诉用户用发版附件里的 `board-skills.zip` 重新安装 skill（或在 Board 仓库执行 `node scripts/build-skill-bin.mjs --host`），不要自己装。它说这个 `board`「是旧版，没有 start / submit / giveup」时，同样停下来把这句话告诉用户，不要改用别的命令拼出同样的步骤。
1. **名字和心跳**：处理卡片的会话不用单独准备。第一次 `board start … --agent <你实际运行的 agent 标识>`（claude、codex、dsh；见「处理一张卡片」第 1 步）一起做好：名字由 Board 按机器设置生成（`<agent 标识>-<机器名>/<模型名>`，例如 `dsh-win/deepseek-v4.1-flash`、`claude-mbp/opus-5.5`），后台心跳随之启动，输出里写着这次用的名字（`--json` 里是 `session.name`）。同一个会话里之后的 `board start` 接着用这个名字和心跳，不用再带 `--agent`。
   - 同一台机器同一 agent 已经有在线会话时，Board 在模型名后面加 `-2`、`-3`……；名字太长时截断模型名，序号留在最后。这台机器没跑 board host、白板不在这台机器时，退回 `<agent 标识>/<模型>`（例如 `codex/codex`）。
   - 名字记在本机：之后的命令不写 `--as` / `BOARD_AS` 就用这个名字；在别的终端、别的进程里跑的命令带上输出里的名字（`--as <名字>`）也行。
   - 后台心跳每 10 秒发一次，同时维持你的名字在线和你持有的所有卡片，干多久都不会被释放。它跟随你的进程（Claude Code、Codex 等）：你的进程不在了（崩溃、被关掉），它跟着停下，不发 final；服务端连续 5 次（50 秒）收不到心跳，名字离线，你持有的卡片回到领取它时所在的可领取状态最上面。
   - **第一条命令不是领卡的会话**（只建卡、拆解、整理）：`board check --agent <标识>`，**单独执行、看它的结果**，成功后 `board heartbeat start`（整个会话只执行这一次）。之后再 `board start` 时接着用这个名字和心跳。
   - 自己起名字（旧写法、要指定名字时）：把 `--agent <标识>` 换成 `--as <名字>`，例如 `claude/opus-5.5`。两段都只能用小写字母、数字、`.`、`-`，以字母或数字开头，只有一个 `/`，总长不超过 48 个字符；被在线会话占用时返回 `NAME_TAKEN`，加一个和本会话相关的后缀再来。之后所有命令都用成功的那个名字，同一个脚本里不能接着用原来的名字。
   - 反例（2026-11-11 真实发生过）：一个会话的脚本里 check 得到了 `NAME_TAKEN`，没看结果，接着用这个名字打标签，最后 `board heartbeat stop`，把另一个会话的心跳停了、名字下线了，那个会话正在做的卡差点被释放。
   - 占用名字时服务端会发一个会话标识，`board` 记在本机，心跳和 `stop` 都带上它：别的会话停不掉你的心跳，你也停不掉别人的（`NAME_TAKEN`，写明是哪个进程）。用了别人的名字做别的事时，输出里会有一行提醒（`--json` 里是 `warning`），看到就换名字。
2. **之后每条命令带白板**（名字不写时用记在本机的那个）：`--board <项目>/<白板>`，或前缀 `BOARD=<项目>/<白板>`；想明确写名字时也带 `--as <名字>` 或前缀 `BOARD_AS=<名字>`，例如：

   ```sh
   BOARD=mini/main board start 2 --agent dsh --json
   board comment 2 "进展" --board mini/main --as dsh-win/deepseek-v4.1-flash
   ```

   你的每条命令都在新的 shell 里跑，`export` 留不到下一条；名字记在本机的状态文件里，不用每条都带。本 skill 各文件里的命令为了简洁省略了这两个参数。
3. **多行内容写进文件再传**：卡片描述、评论（交审评论就有多行）在 Windows 上**必须**这样传：`board.cmd` 要经过 cmd.exe，参数里的换行会把整条命令截断在第一行，只剩第一行被保存。先把内容写进一个 UTF-8 文件（例如会话的临时目录里），再用：

   ```sh
   board new "<标题>" --body-file <文件> [--label <标签>]…
   board edit <ID> --body-file <文件>
   board comment <ID> --comment-file <文件>
   board submit <ID> --comment-file <文件> [<截图>…]
   board giveup <ID> --comment-file <文件> [<日志>…]
   ```

   文件写 `-` 时从标准输入读。其他平台直接写在 `--body "…"` 里也行；只有一行的内容照常写在参数里。

worktree 不在这里创建：会话里第一次处理要改代码的卡片时才创建（见「代码」）。

**连接服务端**：`board` 只通过服务端读写白板。服务端地址和访问令牌由用户用 `board login` 写进 `~/.board/config.toml`，你不用设置。

- 得到 `NOT_LOGGED_IN` 时停下来，请用户运行 `board login --url <服务端地址> --token <令牌>`（令牌在界面「Agent → 访问令牌」新建）。不要自己去找令牌。
- 令牌是密钥：不要写进代码、提交、卡片评论或输出里。
- 名字只是你的身份，和令牌无关；同一个令牌可以被多个不同名字的 agent 使用。名字由 Board 按机器设置生成（`board check --agent <标识>`）时，同一台机器上的几个会话自动分到 `-2`、`-3`；机器设置里换了模型、改了机器名，下一次 check 换成新名字（旧记录会清掉）。

## 处理一张卡片

`board start <ID>` → 开工 → 干活 → 推送 → 交审（`board submit <ID>`）；做不下去时 `board giveup <ID>`。不改代码的卡片（调研、整理之类）跳过开工和推送。

**先领卡，再干活**：拿到卡片引用（带 ID 的卡片，或从 `board ls` 里挑中的那张）后，第一条和这张卡片有关的命令必须是 `board start <ID>`。领取成功之前：

- 不 `board show` 这张卡片，不读它的代码、不调研、不开工；
- 不发和这张卡片有关的进展（例如「开始读取 #69」「已定位到……」）。名字上线不等于领到了卡片。

原因：领取之前卡片随时可能被别的 agent 领走，之前读的代码、做的调研和改动都白费；卡片耗时从领取后的第一次心跳开始算，领取前做的事不计入，耗时会偏短、失真。卡片描述、动态、附件都在 `board start --json` 的返回里，领到之后再读。

1. **领取**：`board start <ID> --agent <你实际运行的 agent 标识> --json`（会话里第一次带 `--agent`，之后可以不带；由 board host 启动的会话不用带）。一条命令做完：这个会话还没有名字时占用名字并启动后台心跳（见「会话开始」第 1 步）、领取、下载附件，然后返回卡片的全部字段：标题、描述（验收标准在这里）、标签、动态。**先读动态**：人的意见、被打回的原因都在里面。返回里还有：
   - `files`：附件已经下载到本地，每个带 `path`。**有附件先看**（截图、日志常常就是问题本身）。
   - `review`、`giveup`：交审、做不下去时卡片会去的状态。`board submit`、`board giveup` 自己会把卡片移过去，不用你从工作流里认；`giveup` 为空表示这块白板没有错误节点、也没有需要人处理的状态。
   - `repo`、`branch`：项目的代码仓库和集成分支（`branch` 为空时按「代码」一节的顺序认）。
   - `session.resumed` 为 true：这张卡本来就在你手里（上次没做完的），接着做。
   - 领取后的第一次心跳开始这一次计时（动态里记「开始第 n 次」），交审或做不下去时结束，卡片上显示累计耗时。
   - `NOT_IN_TODO`：用 `board show <ID> --json` 看它在哪：
     - 「未整理」（inbox）：按 plan.md「整理未整理的条目」处理
     - 在其他状态，或别人持有：不要动，告诉用户它现在的状态
   - `ALREADY_HOLDING`：你在这块白板上还拿着另一张卡片，先把那张做完，或按第 6 步交给人处理
2. **开工**：按「代码 → 开工」准备好 worktree。
3. **干活**：按描述和验收标准在 worktree 里改代码、跑测试。耗时较长时用 `board comment <ID> "<进展>"` 记进度。后台心跳在，干多久都不会被释放。
4. **推送**：按「代码 → 推送」把改动压成一个提交，推到集成分支。
5. **交审**：评论写清楚改了什么；改了代码的卡片，评论最后固定写四行：

   ```
   提交：<sha>
   集成分支：<推到的分支>
   检查：<跑了哪些，结果>
   碰到的别的卡：<board touched 的最后一行；有的话逐条写是不是有意的、为什么>
   ```

   「碰到的别的卡」见「代码 → 推送」第 4 步：复盘的人靠这一行看出这次提交有没有动到别的卡刚做的改动，没有就写「无」。

   **交审用一条命令**，证据作为文件参数一起带上（截图、日志、测试输出、录屏之类；界面改动必须有截图，改前改后、深浅色等），图片在评论里直接显示：

   ```sh
   board submit <ID> --comment-file <交审评论文件> [<截图> <日志>…]
   ```

   它上传附件、发交审评论、结束这张卡片的计时、把卡片移到交审状态，服务端在一次写入里做完：不用再 `board heartbeat final`、`board move`，也不会出现结束计时之后没移走、领取被释放。

   - 不许只写「截图见本地」「日志在 /tmp/…」这类别人打不开的路径。
   - 不许先交审、再补一条只有附件的评论：证据和说明在同一条里。
   - 没有可上传的证据（纯文档、没有界面、截不了图）时，在交审评论里写一句为什么没有。
   - 被拒绝并写着「交审评论缺这几行」：改了代码的卡片，上面四行一行都不能少，补上再交；这张卡确实没改代码（调研、整理）时加 `--no-code`。
   - `FORBIDDEN_COLUMN`：这块白板没有交审状态。按第 6 步 `board giveup`，评论里写明已经做完、推到了哪个提交，等人处理。

   交审之后卡片不再由你持有。worktree 留着做下一张卡。
**做卡时发现的新需求**：干活时发现的、不属于这张卡的改动（顺手看到的 bug、要另做的功能、文档缺口），一律 `board new "<标题>" --inbox --body-file <描述文件>` 记进「未整理」，不直接建进可领取状态，也不顺手在这张卡里做；描述里写明是做哪张卡时发现的（例如 `做 default/main#12 时发现：…`）。放不放进工作流由人决定。

6. **做不下去**（需要人确认，或者冲突解决不了、检查不过又修不好）：改了代码的先按「代码 → 做不下去」把没完成的改动推到 wip 分支。然后一条命令交给人：

   ```sh
   board giveup <ID> --comment-file <原因文件> [<报错截图> <日志>…]
   ```

   评论写原因，或需要人确认的问题（推了 wip 分支的，再写一行 `未完成的改动：wip/<白板标识>/<ID>`）。它上传附件、发评论、结束这张卡片的计时、把卡片移到错误节点（没有错误节点时移到需要人处理的状态）。输出里说「没有错误节点和需要人处理的状态」时，卡片 50 秒后回到领取前的状态：停下来告诉用户。不要自己把卡片放回可领取状态。

## 代码

卡片不需要改代码时，跳过本节。

| 项 | 规定 |
|---|---|
| 集成分支 | 按这个顺序认：项目设置里的「集成分支」（`board flow --json` 的 `branch`，不是空的时候）→ 仓库根目录 AGENTS.md / CLAUDE.md 写明的分支 → 远端的默认分支（`git symbolic-ref --short refs/remotes/origin/HEAD` 得到 `origin/<分支>`；没有输出时用 `git ls-remote --symref origin HEAD` 查）。下文以 `main` 为例。不建卡片分支 |
| 检查 | AGENTS.md / CLAUDE.md 里规定的推送前检查，跑全部，不只跑改到的部分。仓库没写时停下来问用户 |
| 提交 | 每次领取压成集成分支上的一个提交。第一行按仓库的提交规范写；正文写改了什么、跑了哪些检查；最后一行是 `卡片：<项目>/<白板>#<ID>` |
| 发版 | 由人决定：不主动发版、不顺手打 tag、不改版本号；人新建的卡明确要求发版时按下面「发版」 |

提交信息例如：

```
fix(web): 设置页、登录页按钮圆角统一为 8px

- 设置页、登录页所有按钮圆角改成 8px，深色、浅色主题一致
- 检查：cargo test 通过；npm --prefix web run typecheck 通过

卡片：board/main#21
```

### 会话的 worktree

每个会话一个 worktree，一张卡接一张卡地在里面做。worktree 属于开它的会话，不碰别人的。由 board host 启动、提示词里写着「代码已经备好」的会话，worktree 已经由 board host 建好（就是当前目录），不用按下面创建、也不要删，见 host.md。

- **位置**：主仓库目录是 `git rev-parse --path-format=absolute --git-common-dir` 的上一级；你当前所在的目录也是一个 worktree 时，同样以主仓库目录为准。worktree 放在主仓库目录旁边的 `<仓库目录名>.wt/` 里，目录名是你的名字（`/` 换成 `-`），例如主仓库是 `~/repo/board`、名字是 `claude/opus-5.5` 时，是 `~/repo/board.wt/claude-opus-5.5`。
- **创建**：会话里第一次处理要改代码的卡片时创建。`<仓库目录名>.wt/` 里已经有锁着你名字的 worktree（上次中断后用同一个名字重新 check）就直接接着用。否则先清理，再在主仓库目录：

  ```sh
  git fetch origin
  git worktree add --detach --lock --reason "<名字>" ../board.wt/claude-opus-5.5 origin/main
  ```

  锁的原因写你的名字，别人据此知道它属于谁。之后的开工、推送都在这个 worktree 里做。
- **清理**（创建之前）：看 `git worktree list --porcelain` 里 `<仓库目录名>.wt/` 下面的 worktree，`locked <名字>` 一行就是它属于谁（没有锁的不碰）：
  - 名字还在线（`board doctor --as <名字> --json` 的 `checks` 里 `key` 为 `board_as` 的一项 `status` 是 `ok`）：不碰。
  - 不在线（会话中断），并且没有未提交的改动（`git -C <目录> status --porcelain` 没有输出）、也没有没推到远端的提交（`git fetch origin` 后 `git -C <目录> branch -r --contains HEAD` 有输出，集成分支或 wip 分支都算）：`git worktree unlock <目录>`，再 `git worktree remove <目录>`。
  - 有没推的改动：保留，告诉用户。
- **删除**：会话结束、`board heartbeat stop` 之后，在主仓库目录 `git worktree unlock <目录>`、`git worktree remove <目录>` 删掉自己的 worktree。

### 开工

在自己的 worktree 里：

**每张卡都在最新的集成分支上开工**：第一次卡、同一会话用 `board next` 接到的下一张、从 wip 分支接着做的卡都一样，改代码前都要重新做下面这套同步。不要因为上一张刚推完、`HEAD` 看着新，或 board host 启动时拉过一次就跳过。下文以 `main` 为例，实际用 `board flow --json` 里的集成分支。

1. **先保护现场**：`git fetch origin` 之后检查 worktree 是否干净：

   ```sh
   git status --porcelain
   git branch -r --contains HEAD
   ```

   `git status --porcelain` 没有输出，并且 `git branch -r --contains HEAD` 至少有一行（没有没推到远端的提交），才算干净。不干净时先按下面「worktree 不干净时」处理；在改动保存到远端之前，不 switch、不 rebase、不 reset。

2. **查这张卡是不是已经有提交进了集成分支**：

   ```sh
   git fetch origin
   git log origin/main --grep '^卡片：<项目>/<白板>#<ID>$'
   ```

   有的话先看提交和卡片动态：
   - 动态里还没有这个提交的「提交：」行：上一个 agent 推完、还没来得及交审就中断了。不重做，确认提交满足卡片后直接按「交审」处理。
   - 卡片交审过，又被人拖回可领取状态（复盘打回）：先按第 4 步切到最新集成分支，再按动态里人的意见接着修，然后提交一次，同样带 `卡片：<项目>/<白板>#<ID>`。不改写已经推上去的提交；评论要求回滚时，`git revert --no-commit <sha>` 后按「提交」的格式提交，作为这一次的提交。
3. **卡片动态里有 `未完成的改动：wip/...` 时，从那条分支接着做，并先同步到最新集成分支**：

   ```sh
   git switch --detach origin/wip/main/21
   git rebase origin/main
   ```

   分支名照评论里写的（board host 保存的有时带机器名，例如 `wip/main/21-win`）。冲突按「推送」第 1 步的规则解，保留上游和半成品两边的改动；解不了就按「做不下去」交给人，不要猜。不要直接编辑落在旧提交上的代码：先 rebase，落后多少都一样。board host 的那条评论里还写了上一个 agent 怎么结束的、留下了哪些文件、最后做了什么：先看这些和 `git diff origin/main...HEAD`，弄清做到哪了再接着做，不要从头重做。
4. **否则切到最新的集成分支**：`git switch --detach origin/main`。

需要改代码时，切好后（第 3、4 步）确认基点确实包含最新的集成分支（切到 `origin/main` 时两者相等）：

```sh
git merge-base --is-ancestor origin/main HEAD
```

退出码不是 0 就回到第 1 步重新同步。在旧代码上开工，rebase 时就会和别的卡刚推的改动冲突，解错了会悄悄撤回别人的改动（#328 带回了 #320 删掉的下载按钮）。推送前的 `board touched` 按这一次切换认开工时的基点。

**worktree 不干净时**：

- 先判断是不是上一张卡没收尾的改动。是的话按「做不下去」第 1 步把它提交、推到 `wip/<白板标识>/<上一张卡 ID>`，并在那张卡上评论 `未完成的改动：<分支>`；不要把上一张卡的改动带进当前卡。
- 如果就是这张卡从 wip 分支接着做的改动，保存回它自己的 wip 分支（分支已存在时加 `--force-with-lease`），再按第 3 步同步，不要把本卡半成品当无关改动另存。
- 分不清属于哪张卡、或确认与本卡无关时，不要用 `git stash` 后丢掉，不要 `git reset --hard`、`git checkout -- .`、`git clean`。把现场完整保存成一个远端快照；有未提交的改动时：

  ```sh
  git add -A
  git commit -m "chore: 保存开工前的未收尾改动"
  git push origin "HEAD:refs/heads/wip/main/<当前卡 ID>-presync-$(git rev-parse --short HEAD)"
  ```

  没有未提交的改动、只有没推到远端的提交时，省掉 `git add` 和 `git commit`，直接推 `HEAD`。推完用 `git branch -r --contains HEAD` 确认快照分支已在远端，再在当前卡上评论「开工前发现与本卡无关的未收尾改动，未带入本卡，已保存到 <分支>」。
- 保存失败（`git commit` 或 `git push` 失败）就停在这一步，按「做不下去」在当前卡上说明，现场原样保留；不能为了换分支把这些改动删掉或覆盖掉。

### 推送

在自己的 worktree 里：

1. 把改动提交（可以是多个提交），然后 `git fetch origin && git rebase origin/main`。有冲突自己解决，按这几条：
   - **上游的改动必须保留**：冲突的那一边是别的卡已经推上去的改动。不整份取自己那一版（`git checkout --theirs`、编辑器里整块「接受自己的」），逐块合：把自己的改动叠在上游的新代码上。
   - 先看冲突文件最近被哪些卡改过、改了什么：`git log -5 --format='%h %s%n%b' origin/main -- <文件>`（提交说明最后一行是卡片），读懂再合。
   - **两边都新建的同名文件**（尤其测试）：合成一份，两边的内容都留下，不整份取自己的。
   - **不删、不整份替换别的卡留下的测试用例**。卡片明确要求删的除外，在交审评论里写明删了哪些、为什么。
   - 合不了（看不懂上游为什么这么改、两边的要求互相矛盾）：按「做不下去」交给人，不要猜。
2. 在 rebase 之后的代码上跑仓库规定的全部检查。不在 rebase 之前跑：旧代码上通过，推上去的未必通过。不通过就修好再跑。
3. 压成一个提交：`git reset --soft origin/main`，再 `git commit`，提交信息按上表。
4. **查有没有碰到别的卡**：`board touched`（只用 git，不连服务端）。它列出这次提交删掉了别的卡最近加的行、或加回了别的卡最近删的行，按卡分组，写出提交、文件和例子；「最近」是开工时所在的提交（从本 worktree 的 reflog 认）之后推上来的提交，这张卡自己的提交不算。
   - 退出码 0、最后一行「碰到的别的卡：无」：接着第 5 步。
   - 退出码 1：逐条看列出来的卡。**不是有意的**（多半是解冲突时取了自己那一版、或在旧代码上开工）：对照 `git show <它列的提交> -- <文件>` 把别的卡的改动找回来，回到第 2 步重新跑检查、压提交、再查。**有意的**（卡片要求改掉、同一个功能接着改）：留着，交审评论的「碰到的别的卡」一行照抄最后一行，再逐条写为什么是有意的。
   - 它说「没找到开工时的基点」时按最近 20 个提交查，列出的多半是同一个功能接着改，照样逐条确认；知道开工时的提交可以用 `--base <提交>` 重查。
   - `board` 版本旧、没有这个命令（「未知命令」）：交审评论写「碰到的别的卡：没查（board 版本旧）」，并在评论里列出冲突过的文件。
5. **推之前确认领取仍有效**：`board hold <ID>`。你干活期间卡片可能已经被释放、被别人领走（例如这台机器和服务端断开超过 50 秒被判掉线，卡片回到可领取状态被别的机器接走）。这时再推，集成分支上就会有同一张卡的两份改动。
   - 成功：接着第 6 步。
   - `NOT_HOLDER`（领取已经失效：被释放、被别人领走、被人移走）：**不推集成分支**。按「做不下去」第 1 步把改动推到 `wip/<白板标识>/<ID>`，在卡片上评论「领取已经失效（<错误信息里的原因>），改动推在 wip/<白板标识>/<ID>」，评论最后一行写 `未完成的改动：wip/<白板标识>/<ID>`。然后结束这张卡：不 final、不移动（卡片已经不归你）。由 board host 启动的会话也不再 `board next`，直接结束。
   - `UNREACHABLE`：`board hold` 已经每 30 秒重试、等了 5 分钟还连不上服务端。同样不推集成分支，先把改动推到 wip 分支，再执行一次 `board hold <ID>` 等服务端恢复：能连上了就补上面那条评论（不管 hold 的结果），然后结束这张卡（不 final、不移动）；还是连不上，就在给人的汇报里写明 wip 分支，结束。
6. `git push origin HEAD:main`。被拒（别人先推了）就回到第 1 步：重新 rebase、重新跑检查、重新 `board touched`、重新 `board hold`，再推。推送被拒就是锁：不要 `--force`，不改写集成分支上已有的提交。
7. 这张卡是从 wip 分支接着做的，推上去之后删掉那条分支：`git push origin --delete wip/main/21`。

推上去的提交号（`git rev-parse --short HEAD`）写进交审评论的「提交：」行。

### 做不下去

冲突解决不了，或者检查不过又修不好时，不推进集成分支：

1. 把没完成的改动提交后推到 wip 分支：`git push origin HEAD:refs/heads/wip/<白板标识>/<ID>`，例如 `wip/main/21`。这张卡是从这条 wip 分支接着做的（分支已经存在）时，推的时候加 `--force-with-lease`。
2. 按「处理一张卡片」第 6 步 `board giveup`（评论里带 `未完成的改动：wip/main/21` 一行）。

wip 分支由接着做的 agent 在推进集成分支后删除，或者由人处理完后删除。

### 发版

只在**人新建的卡明确要求发版**时做：`board start --json` 的动态里第一条是「人」新建了卡片，并且标题或描述要求发布新版本。agent 建的、拆出来的卡，或者只是顺带提到「之后要发版」的卡，都不发：做完卡片本身，交审评论里提一句。

1. **认发版流程**：仓库根目录 AGENTS.md / CLAUDE.md 写了发版命令或流程（例如 Board 的 `npm run release -- <版本号> --push`）就照它做，下面几步里它已经覆盖的不重复做。没写时按下面的通用做法。
2. **定版本号**：卡片写了版本号就用它；没写时按仓库写明的规则；仓库也没写时，上一个版本 tag（`git tag --sort=-v:refname`，`v` 加数字开头）的最后一位加 1。这一版的提交里（`git log <上一个 tag>..origin/main`）有 `refactor`、标了「不兼容」的提交，或者你判断算大升级时：停下来按「处理一张卡片」第 6 步交给人，评论里列出这些提交，问升哪一位。远端已经有同名 tag 时（`git ls-remote --tags origin`）同样交给人，不覆盖。
3. **改版本号、写发版记录**（按「开工」在最新集成分支上做）：用仓库已有的脚本改版本号（例如 `scripts/bump-version.mjs`），没有脚本就改仓库里所有写版本号的文件；仓库有 `CHANGELOG.md` 这类发版记录时，按它的格式补上这一版。已经是目标版本、也没有发版记录要写时跳过本步，这张卡不提交，直接第 5 步。
4. **推发版提交**：按「推送」1–6 步推到集成分支（检查、`board touched`、`board hold` 都照做），提交第一行 `chore: 发版 vX.Y.Z`（照仓库的提交规范），最后一行照常是 `卡片：<项目>/<白板>#<ID>`。
5. **打 tag**：在集成分支上要发的那个提交（第 4 步推上去的，跳过第 4 步时是最新的 `origin/main`）打注释 tag，正文是上一个 tag 之后的变更说明（按提交整理，写给用户看），多行正文写进文件再传：

   ```sh
   git fetch origin
   git tag -a vX.Y.Z -F <说明文件> <提交>
   ```

   打之前确认这个提交跑过仓库规定的全部检查（第 4 步跑过的就是它；跳过第 4 步时在它上面跑一遍），再 `board hold <ID>`；`NOT_HOLDER` 时不推 tag，删掉本地 tag，按「推送」第 5 步说的结束这张卡。
6. **推 tag**：`git push origin vX.Y.Z`。推 tag 通常会触发仓库的 Release 流水线；推出去之后**不改、不删、不挪**，发错了再发一个版本。
7. **同步里程碑**：在仓库目录执行 `board versions sync vX.Y.Z`（不用 `--as`、`--board`），给这一版做的卡片打上版本标签，界面「里程碑」里按版本看。仓库的发版命令已经代跑过的不重复跑；失败（命令不认识、服务端还不认这个接口）时把输出写进交审评论，不重试、不当成发版失败。
8. **交审**：按「处理一张卡片」第 5 步交审。评论写版本号和为什么是这一位、tag 打在哪个提交、Release 流水线的链接（有的话，例如 `gh run list --workflow <文件> --limit 1`）、`board versions sync` 的输出；最后四行照常写，跳过第 4 步时「提交：」写「无（版本号已是 vX.Y.Z，tag 打在 <sha>）」。

**人工确认项**：仓库 AGENTS.md / CLAUDE.md 发版一节里写明发版前必须做的事（真机验证、确认密钥之类），你做不了的，在第 5 步之前停下来，按「处理一张卡片」第 6 步交给人，评论里列出来。其他文档里的提醒（待办清单、注意事项）不挡发版，列进交审评论。

## 处理一块白板

循环：`board start --json`（不带 ID，按工作流顺序领可领取状态最上面的；会话里第一次带 `--agent <标识>`）→ 按「处理一张卡片」2–6 处理 → 再 `board start`，直到返回 `EMPTY_TODO`。最后汇报处理了哪些卡片、各自的结果。

## 会话结束

所有卡片都处理完（都已交审或交给人）后，停掉后台心跳，名字立刻离线（由 board host 启动的会话跳过这一步，心跳由 board host 停；一张卡都没领过、也没 check 过的会话没有名字，也跳过）：

```sh
board heartbeat stop
```

然后在主仓库目录删掉本会话的 worktree（见「会话的 worktree → 删除」）。

会话中途得到 `NAME_OFFLINE`：你的名字已经离线（心跳中断超过 50 秒，或后台心跳停了），你持有的卡片可能已经被释放。重新 `board check --agent <标识>`（自己起的名字就 `board check --as <名字>`，被占用就加后缀），再 `board heartbeat start`，然后 `board show <ID> --json` 看卡片现在的状态再决定。
